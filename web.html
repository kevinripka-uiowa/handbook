Web Technical Basics

How websites work and how professionals build them: code and builders, hosting, files and links, responsive design and text sizes, media, embeds, writing, share previews, and accessibility.

Most of this applies whether you write code, use a site builder, or work in a newsroom or company content management system.

How a website works

Files and folders on a server

A website is files and folders, the same kind you have on your own computer. They're stored on a server: a computer that's always on and connected to the internet, set up to send those files to anyone who asks.

The address of a page is mostly the path to a file in those folders:

Files on the server        Address in the browser
ballpark-site/
  index.html               example.com/
  schedule.html            example.com/schedule.html
  players/
    index.html             example.com/players/
  images/
    logo.svg               example.com/images/logo.svg
  styles.css

A file named index.html is the page a folder opens to, so the address can leave it off. Site builders and CMSs hide the files from you, but they're still there. The builder makes and stores them for you.

From address to page

  1. Someone types an address or taps a link.
  2. The domain (uiowa.edu) is looked up to find the computer, called a server, that stores the site.
  3. The server sends the page's files to the browser.
  4. The browser reads the files and draws the page on that person's screen.

The last step matters most for design. The browser builds the page on every screen separately, so the same page looks different on a phone, a laptop, and a large monitor.

Parts of a web address

PartExampleWhat it is
Protocolhttps://How the page is sent. The s means the connection is encrypted. Every site should use https.
Subdomainclas.A section of a domain, often its own site
Domainuiowa.eduThe name you register and pay for each year
Path/journalism/studentsThe page within the site, often matching folders
Anchor#contactA spot on the page. The browser jumps to it.

HTML, CSS, and JavaScript

Every web page is made of three kinds of code, whether you write it or a tool writes it for you.

  • HTML is the content and its structure: headings, paragraphs, links, images, lists.
  • CSS is the appearance: fonts, colors, spacing, and layout at different screen sizes.
  • JavaScript is behavior: menus that open, maps you can drag, charts that respond.

Keeping them apart is why a site can be redesigned without rewriting its content, and why a screen reader can read a page aloud from its HTML.

Everyone who publishes on the web should know basic HTML. You'll see it in CMS code views, embed codes, email newsletters, and site builders' code blocks, and it's how you fix what a visual editor gets wrong. CSS and JavaScript are worth knowing at least well enough to recognize.

HTML

HTML marks up content so the browser knows what each part is. Each part is wrapped in tags: an opening tag, the content, and a closing tag with a slash.

<p>The Kernels won 4–2 on Friday.</p>

The tags and what's between them make an element. This one is a paragraph.

The tags to know first

TagWhat it isExample
<h1> to <h6>Headings. h1 is the page title. h2 starts a section, h3 a part of a section.<h2>Schedule</h2>
<p>Paragraph<p>Gates open at 6.</p>
<a>Link. href is where it goes.<a href="schedule.html">See the schedule</a>
<img>Image. src is the file, alt is the alt text. No closing tag.<img src="images/cardinal.jpg" alt="A male cardinal on a feeder">
<ul>, <ol>, <li>Bulleted list, numbered list, and each item in it<ul><li>Tickets</li><li>Parking</li></ul>
<strong>, <em>Strong importance (bold) and emphasis (italic)<strong>Rain date:</strong> Sunday

Choose tags for what the content is, not how it looks. A heading is an h2 because it starts a section, not because you want big bold text. Screen readers and search engines depend on this. See Accessibility.

A whole page

<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Bird Count 2026</title>
</head>
<body>
  <h1>Bird Count 2026</h1>
  <p>Volunteers counted 84 species in Johnson County.</p>
  <p><a href="results.html">See the full results</a></p>
</body>
</html>
  • The head holds information about the page, like the title in the browser tab. It doesn't show on the page.
  • The body holds everything that shows.
  • Elements go inside other elements. Close them in reverse order.

Try it

  • In a browser: W3Schools' "Try it Yourself" editor lets you change HTML and see the result, on any device.
  • On a computer: type the page above into a code editor such as Visual Studio Code, save it as index.html, and open it in a browser.
  • On any website: right-click part of a page and choose Inspect to see its HTML. In Safari, turn on the developer features first. See Check on a phone.

Learn more: W3Schools HTML Tutorial. For more depth, MDN Web Docs: Learn web development.

CSS

CSS controls how HTML looks. A CSS rule picks elements and sets their style:

h1 {
  font-family: Georgia, serif;
  color: #000000;
}

p {
  font-size: 18px;
  line-height: 1.5;
  max-width: 65ch;
}
  • The selector (h1, p) says which elements the rule applies to.
  • Inside the braces, each property gets a value, ending with a semicolon.
  • CSS usually lives in its own file, such as styles.css, linked from the head of every page: <link rel="stylesheet" href="styles.css">. Change the file, and every page changes.

Properties to know first

PropertyWhat it sets
font-family, font-size, font-weightTypeface, size, and weight
line-heightSpace between lines of text
color, background-colorText color and background color, as hex codes such as #FFCD00
margin, paddingSpace outside and inside an element's edges
max-widthThe widest an element can get. Keeps lines of text readable on large screens.

Different screen sizes

A media query applies rules only at certain screen widths. This is how a layout changes between a phone and a laptop:

h1 { font-size: 30px; }

@media (min-width: 800px) {
  h1 { font-size: 48px; }
}
  • The headline is 30 px on phones and 48 px on screens 800 px wide and wider.
  • Body text has no rule here, so it stays the same size on every screen. That's on purpose. See Leave body text at its size.
  • Professionals often write sizes in rem instead of px. 1rem is the reader's browser text size, 16 px unless they've changed it, so text grows for readers who set larger text.

See Responsive design.

Learn more: W3Schools CSS Tutorial.

JavaScript

JavaScript makes a page respond: menus that open, maps you can drag, charts that change when you tap them, forms that check what you typed. Most media makers don't write much JavaScript, but you'll paste it in embed codes and see it in code from AI tools and templates.

<button id="more">Show the box score</button>
<p id="score" hidden>Kernels 4, Loggers 2</p>

<script>
  document.getElementById("more").addEventListener("click", function () {
    document.getElementById("score").hidden = false;
  });
</script>
  • JavaScript goes inside <script> tags, or in its own file linked with <script src="...">.
  • This example finds the button by its id, waits for a click, then shows the hidden paragraph.
  • Only paste scripts from sources you trust. A script can change anything on the page and send readers' information elsewhere.
  • Keep important content in the HTML, not only in JavaScript. If the script fails, the content should still be there.

Learn more: W3Schools JavaScript Tutorial.

The University of Iowa's sites are built in SiteNow, a CMS based on Drupal. Most newsrooms and companies use a CMS, so expect to publish into a template someone else built.

Code written by AI

AI tools write working HTML, CSS, and JavaScript quickly. You're still responsible for it.

  • Decide what the page should do and how it should look before you ask.
  • Read the code. Know what each part does well enough to change it.
  • Test it on a phone and with a keyboard. AI code often skips accessibility.
  • Check what it loads from other sites. Scripts from unknown sources can break or track readers.

More on using AI responsibly is on the AI page.

Hosting and domains

  • A domain is the address. You rent it from a registrar for a year at a time, usually $10–20 a year for a .com. If the renewal lapses, someone else can buy it.
  • Hosting is the server space where the files live. Site builders include it. Hand-coded sites need a host, such as GitHub Pages.
  • A free address such as yourname.wixsite.com or username.github.io works for class. For a portfolio you'll share with employers, a custom domain looks more professional.

Who owns it

When you build a site for a client or organization, the domain and hosting accounts should be in their name, not yours. Otherwise they lose the site when you leave. Hand over the logins in writing at the end of the project.

Files and links

Naming files

  • Lowercase letters, numbers, and hyphens only: spring-game-poster.jpg.
  • No spaces. A space becomes %20 in the address and can break links.
  • Names are case-sensitive on most servers. Photo.JPG and photo.jpg are different files. A link that works on your computer can break once it's online.
  • The home page of a site or folder is named index.html.

Absolute and relative links

  • Absolute: the full address, https://uiowa.edu/admissions. Use for other sites.
  • Relative: a path from the current page, images/cardinal.jpg or ../index.html. Use within your own site, so it keeps working if the domain changes.

Never link to a file on your own computer, such as file:///Users/ or C:\. It works only on your computer.

Links that open a new tab

Let links open in the same tab unless the reader is in the middle of something they'd lose, such as a form. Readers know how to open a new tab themselves.

Responsive design

More than half of web visits are on phones. A page has to work from about 320 px wide to wider than 2000 px. Responsive design means one page adjusts its layout to fit each screen. You don't build a separate phone site.

What changes on a phone

Part of the pageOn a phone
Body textStays the same size. Lines get shorter, and the text reflows onto more lines.
ColumnsStack into one column, top to bottom.
Headlines and other large textGet smaller, so a headline doesn't fill the screen.
Images and videoShrink to fit the width of the screen and keep their proportions.
MenusCollapse behind a menu button.
Margins and space between sectionsGet smaller, so the content uses the width of the screen.
Buttons and linksStay the same size, so they're easy to tap.

Leave body text at its size

Don't shrink body text to make the phone version look like the desktop version. People hold a phone closer to their eyes than a laptop screen, so text at the same size reads at about the same size on both. Let the text reflow. If a reader has to pinch to zoom, the text is too small.

Don't make body text bigger on large screens either. Keep the size and limit how wide the lines get. See Text sizes from desktop to phone.

When columns stack

  • Columns stack in order, left column first. Check that the order still makes sense on a phone: a photo above its caption, the story before the sidebar.
  • Side-by-side comparisons, such as before and after photos or two charts, end up one above the other. Label each one so the comparison still works.
  • Tables with many columns don't stack. Let them scroll sideways inside their own box, or turn them into a list.

Images and video shrink to fit

  • Site builders and video players from YouTube and Vimeo shrink to fit on their own. In hand-coded pages, one CSS rule does it: img { max-width: 100%; height: auto; }.
  • Text in an image shrinks with the image. A graphic that's readable on a laptop can be unreadable on a phone. Make a phone version with larger text, or put the words on the page instead.
  • Wide images get short. A panorama or a wide chart can end up a thin strip on a phone. Try a taller crop or a phone version.
  • Embed codes with a fixed width run off the screen. See Embeds.

Breakpoints

  • A breakpoint is a screen width where the layout changes, such as when columns stack. Site builders let you edit the layout at each one. Check every one.
  • Design for the phone first when most of your audience reads on phones. News and social traffic is mostly phones.

Text sizes from desktop to phone

Text on a page does one of two jobs, and each is sized a different way:

  • Reading text, such as stories, headlines, and captions. Body text stays the same size on a phone, 16–22 px. 16 px is the most common. Headlines get smaller.
  • UI text, such as buttons, menus, and form fields. It stays the same size on every screen. Buttons and menu links are 16–18 px.

Full size tables for headlines, captions, buttons, and HTML email are on Type: Web page sizes and Type: HTML email sizes.

Check on a phone

Preview the page at phone width while you work, then open the published page on a real phone. Look for text too small to read, buttons too close to tap, and anything that scrolls sideways.

Text often looks a different size on a real phone than in a phone-width preview on a computer. The preview doesn't show everything a phone does:

  • Phone pixels are smaller. A phone fits more pixels into an inch than a computer screen, so 18 px text is physically smaller on a phone. A 375 px preview on a monitor is much wider than a real phone. Judge text size on the phone, held where you'd read it.
  • Phones enlarge some text on their own. Safari on an iPhone can make text bigger when the phone is turned sideways. Chrome on Android can enlarge text in wide blocks. A computer browser does neither.
  • Readers change their settings. Many people set larger text on their phones or zoom pages in the browser. Your phone may not match your reader's. The page should still work when text is bigger.
  • A page missing its viewport setting shows up on a phone as a tiny desktop page. A narrow computer window doesn't show the problem. Site builders handle this for you. Hand-coded pages and code from AI tools sometimes leave it out.

Site builders handle most of this. If you write your own code, two lines fix the viewport setting and the automatic enlarging: <meta name="viewport" content="width=device-width, initial-scale=1"> in the head, and html { text-size-adjust: 100%; -webkit-text-size-adjust: 100%; } in the CSS. Use 100%, not none, which can stop readers from zooming.

Where to find it: In Chrome, View › Developer › Developer Tools, then the device button at the top left of the panel. In Safari, turn on Settings › Advanced › Show features for web developers, then Develop › Enter Responsive Design Mode. Site builders have a phone preview button in the editor.

Images, video, and fonts

Images

  • Export at twice the size it displays, so it's sharp on high-density screens. An image shown 800 px wide should be 1600 px wide.
  • Keep file size down. Aim for under 500 KB for a large photo, much less for small images. Large images make pages slow on phone data.
  • Use JPG or WebP for photos, PNG or SVG for logos and graphics with flat color.
  • Write alt text. See Accessibility.

Formats, sizes, and compression are on Graphics: Exporting for screens.

Video and audio

Don't upload video files to a page. Upload to YouTube or Vimeo and embed the player, which adjusts quality to each reader's connection. Do the same with audio and a podcast or audio host. See Video: Exporting.

Fonts

  • A web page can only use fonts the browser can load. Use the site builder's fonts, a web font service such as Adobe Fonts or Google Fonts, or system fonts already on every device.
  • Desktop font licenses often don't cover web use. Check before you upload a font file.
  • Each font weight is a separate download. Two or three weights are usually enough.

Font files and licenses are on Type: Font files and licenses.

Embeds

An embed shows something hosted on another site inside your page: a video, a Datawrapper chart, a map, a social post. You paste an embed code, usually an <iframe>, into the page.

  • It depends on the other site. If the original is deleted, made private, or the service shuts down, your page shows an empty box. For important material, keep a screenshot or a copy you have rights to.
  • Check it on a phone. Some embed codes set a fixed width and run off small screens. Look for a responsive embed option.
  • Builders may limit custom code. Some only allow embed codes on paid plans or in a specific block type.
  • Embeds load other sites' scripts, which can slow the page and track readers. Use only what the story needs.

Embedding a post usually doesn't need permission. Downloading it and re-uploading it does. See Rights and Credit.

Writing for the web

People scan web pages before they decide to read. Search engines and screen readers depend on the same structure.

  • Page title. The text in the browser tab and in search results. Make it specific, about 60 characters or fewer: "Hawks beat Iowa State 4–2" not "Home".
  • Headings in order. One main heading (H1) per page, then H2s for sections and H3s inside them. Choose a heading level for its place in the outline, not for its size. Change the size with styles.
  • Front-load. Put the important words at the start of headings, paragraphs, and links. Readers scan the left edge.
  • Short paragraphs. One idea each. On a phone, a 6-line paragraph fills the screen.
  • Link text says where it goes. "Download the 2026 schedule (PDF)," not "click here." Screen reader users often skip from link to link.
  • Interface text. Button labels, menus, and form fields are writing too. Use plain words and say what happens: "Subscribe" or "Send message," not "Submit."

Share previews

When a link is posted on social media or in a text message, the app shows a preview card with an image, a title, and a description. The page sets these with hidden tags called Open Graph tags.

PartGuideline
Image1200 × 630 px, JPG or PNG. Keep text and faces near the center: some apps crop it to a square.
TitleUsually the page title. About 60 characters.
DescriptionOne or two sentences, about 150 characters. Write it. Otherwise the app picks text from the page.

Site builders and CMSs have fields for these, usually in the page's settings under SEO or Social. Apps save a copy of a preview, so a fix may not show on a link that's already been posted. Facebook's Sharing Debugger and LinkedIn's Post Inspector make them refresh.

Accessibility

Web accessibility is measured against the Web Content Accessibility Guidelines (WCAG). Level AA is the usual requirement. A federal rule from 2024 requires public universities, including Iowa, to meet WCAG 2.1 AA on their web content.

  • Alt text on every meaningful image: what it shows that matters to this page, in a sentence or so. Screen readers read it aloud. Don't start with "Image of."
    • For a poster or flyer, include all the text on it.
    • For a chart, give the main finding, not every number.
    • For a decorative image that adds no information, leave the alt text empty so screen readers skip it.
    Alt text is different from a caption. A caption is visible to everyone and adds context. Alt text replaces the image for people who can't see it, so a published photo usually needs both.
  • Text in images isn't readable by screen readers or search. Put important words in the page text, or in the alt text.
  • Contrast: text needs enough contrast with its background for people with low vision, and for anyone reading in bright sun.
    • Normal text: at least 4.5 to 1. This is regular text below 24 px, or bold text below 18.66 px.
    • Large text: at least 3 to 1. This is regular text 24 px or larger, or bold text 18.66 px or larger. (WCAG sets these as 18 pt and 14 pt bold.)
    • Important graphic shapes, such as chart lines, icons, and button edges: at least 3 to 1.
    Check your colors with the contrast checker below, or search "WebAIM contrast checker" and paste in both hex codes.
  • Don't use color alone to carry meaning. About 1 in 12 men has some form of color blindness. Underline links in body text. If a chart or map uses red and green to show a difference, add labels, patterns, or a second difference such as light versus dark.
  • Headings in order and link text that says where it goes. See Writing for the web.
  • Reflow: at 320 px wide, or zoomed to 400% on a laptop, the page should read without scrolling sideways. Text zoomed to 200% shouldn't get cut off or overlap.
  • Keyboard: every link, button, and menu should work with the Tab and Enter keys. Try it.
  • Captions on video and transcripts for audio. See Video and Audio.
  • Embedded charts and maps need a text version of the main point, in the text around them or in the alt text.

Automatic checkers such as WAVE find missing alt text, low contrast, and skipped headings. They can't tell whether alt text is accurate or a page makes sense when read aloud. Check those yourself.

Before you publish

  • Click every link and button on the published page, not the preview.
  • Open it on a phone. Read the whole page there.
  • Check every image has alt text, every video has captions, and nothing is pixelated or huge.
  • Proofread the title, headings, captions, and buttons. Errors in headings are the most visible.
  • Paste the link into a message to yourself and check the share preview.
  • Check credits for every photo, graphic, video, and song you didn't make. See Credit lines.

Quick answers

Why does my site look different on my phone?
The layout changes at different screen widths. Edit the phone version, or the layout at each breakpoint. See Responsive design.
Should text be smaller on a phone?
Body text, no. Leave it at its desktop size and let it reflow. Headlines, yes. UI text such as buttons and menus stays the same. See Text sizes from desktop to phone.
Why does my image show on my computer but not online?
The file name's capitals don't match the link, the file wasn't uploaded, or the link points to your computer. See Files and links.
Why is my page slow to load?
Usually large images, uploaded video, or too many embeds. Resize images and embed video from a host. See Images, video, and fonts.
Why does my link preview show the wrong image?
The share image isn't set, or the app saved an old preview. Set the image in the page settings and refresh it with the platform's debugger. See Share previews.
Why does my embed show an empty box?
The original was deleted or made private, the builder blocks custom code on your plan, or the code was pasted into the wrong kind of block. See Embeds.
Do I need my own domain?
Not for class. For a portfolio you send to employers, it's worth the yearly fee. See Hosting and domains.
